# v0.6.0 本地测试版

此版本尚未上传 GitHub、合并 main 或发布 Release。

## 修复与新增

- 修复保存时错误选中模型列表第一项，导致所选模型和实际分析模型不一致。
- 供应商配置统一处理：每个供应商独立保存 API key、地址、协议、模型列表、当前模型和请求参数；切换后不会重新补入已删除的默认模型。
- OpenRouter、Poe、自定义供应商不再借用 OpenAI 的默认模型。升级时清理旧版本为其他内置供应商插入的裸 `gpt-5-mini`，保留其他模型及原始配置备份。
- 当前模型改成下拉菜单；通过加号输入模型 ID，结构化连接测试通过后才能加入。模型可以移除。
- 供应商下拉菜单支持添加多个自定义供应商，分别命名、配置地址，并选择 OpenAI-compatible 或 Anthropic Messages 协议。
- 连接测试验证 JSON 字段和类型，空回复、纯文本 OK 或错误结构不会被判为成功。测试成功仍不等于完整长篇岗位分析必然成功。
- API 请求拒绝空模型、无效地址和不安全的远程 HTTP 地址；测试时按需申请该供应商站点权限。
- 失败结果显示尝试的供应商及模型，记录失败调用耗时；不会偷偷回退到其他供应商或默认 GPT。
- 重整 Strict、Balanced、Potential、Sponsorship-first 提示词，共用证据要求和 JSON 格式，分别定义评价偏好。自定义提示词仍可控制评分，但必须保留输出结构。
- 修复“荷兰岗位但不需要 sponsorship”时提示词自相矛盾的问题。不推测 JD 未写出的经验年限，不把 sponsor 名录匹配说成岗位保证提供签证。

## 保留数据更新

1. 在 `chrome://extensions/` 打开原扩展的“详细信息”，记下扩展 ID 和加载来源文件夹。不要卸载原扩展。
2. 关闭插件侧栏、暂停正在进行的分析，临时关闭原扩展开关。
3. 备份原扩展文件夹，再解压 `linkedin-job-match-v0.6.0.zip`。
4. 把解压后包含 `manifest.json` 的那一层内容复制到**原加载来源目录**，覆盖同名文件；不要更换目录，也不要把 ZIP 重新拖成另一个插件。
5. 打开原扩展开关并点击“重新加载”。确认同一个扩展 ID 下版本变成 0.6.0。
6. 刷新 LinkedIn / Indeed 页面，重新打开 Settings，核对供应商和模型后保存。

扩展数据位于 Chrome 的扩展存储中，不在安装 ZIP 内；保留同一扩展身份才能继续使用原数据。升级只处理模型配置，不重算或改写旧简历、历史、收藏和岗位记录。第一次保存新配置前，会在本机保存一份旧配置备份 `ljm_config_before_v060`，其中可能包含旧 API key，请勿导出公开。

首次安装：解压后通过“加载已解压的扩展程序”选择包含 manifest.json 的目录。

## 建议测试顺序

1. OpenRouter：选择或添加自己实际可用的完整模型 ID，测试通过并保存，再重新分析一个岗位；检查 Debug 的 Provider/Model 与选择一致。
2. 添加第二个模型并选中它；确认保存后不会跳回列表第一项。
3. OpenRouter → Gemini → OpenRouter：地址、Key、模型列表和当前模型应各自保留。
4. 移除不想要的默认模型，切换供应商和重开侧栏后确认它不会重新出现。
5. 新增两个不同的自定义供应商，确认两者可分别配置并保存。
6. 输入错误模型或返回无效 JSON 的模型，应显示失败且不加入模型列表。
7. 检查旧简历、历史、Saved、Inserted 和标题胶囊设置仍在；旧记录的模型名属于当时分析，不随设置改写。

设置保存用于后续请求。要检查新配置，请点击 Re-analyze，不要仅查看旧历史或缓存记录。

## 验证范围

本地自动化覆盖配置隔离、旧版迁移、活动模型选择、请求地址、结构化测试及正式分析路径；网络响应使用模拟数据。真实供应商和具体模型仍需使用者用自己的 API key 验收。不要把 Key 发到 GitHub 或聊天截图里。
